# Graphs

A graph $G = (V, E)$ is a set of **vertices** together with a set of **edges** connecting pairs of them. That's all — and that's exactly why graphs are so powerful. Road networks, social networks, the web, circuits, course prerequisites, the moves of a puzzle, the states of a game, the pixels of an image: all of them are graphs once you decide what the vertices and edges are.

This chapter has two goals. The first is to master a small toolkit of classical algorithms — breadth-first search, depth-first search, topological sort, minimum spanning trees, shortest paths — each of which runs in (nearly) linear time. The second, and more important, is to learn to **model**: to look at a problem that doesn't mention graphs at all and see which graph, and which classical question about it, the problem is secretly asking.

!!! tip "Take-Home Lesson"
    Designing novel graph algorithms is very hard, so don't do it. Instead, design **graphs** that let you use classical algorithms. Most graph interview problems are one of a dozen standard algorithms applied to a cleverly chosen graph.

---

## Flavors of Graphs

The first step in any graph problem is to identify what kind of graph you have, because it determines which algorithms apply.

| Property | Question to ask | Why it matters |
|---|---|---|
| **Directed** vs. undirected | Does an edge $(x, y)$ imply $(y, x)$? | Prerequisites, one-way streets, and "follows" relations are directed. Cycle detection and connectivity work differently. |
| **Weighted** vs. unweighted | Do edges have costs? | Unweighted shortest paths: BFS. Weighted: Dijkstra and friends. |
| **Sparse** vs. dense | Is $E$ closer to $V$ or to $V^2$? | Chooses the representation, and between some algorithms. |
| **Cyclic** vs. acyclic | Can you return to where you started? | Directed acyclic graphs (DAGs) admit topological order, which makes many hard problems easy. Trees are connected acyclic undirected graphs. |
| **Implicit** vs. explicit | Is the graph given, or generated by rules? | Grids, puzzle states, and word ladders are graphs you never build in full; you generate neighbors on demand. |
| **Simple** vs. non-simple | Self-loops $(x, x)$? Repeated edges? | Many implementations quietly assume a simple graph. |

## Representations

| | Adjacency list | Adjacency matrix | Edge list |
|---|---|---|---|
| Space | $O(V + E)$ | $O(V^2)$ | $O(E)$ |
| Is $(x, y)$ an edge? | $O(\deg x)$ | $O(1)$ | $O(E)$ |
| Iterate over neighbors of $x$ | $O(\deg x)$ | $O(V)$ | $O(E)$ |
| Best for | Almost everything | Dense graphs, Floyd–Warshall | Kruskal, Bellman–Ford |

!!! tip "Take-Home Lesson"
    Adjacency lists are the right data structure for most applications of graphs. Traversal algorithms spend their time iterating over neighbors, and adjacency lists make that proportional to the number of edges that actually exist.

In Python, an adjacency list is a `list` of lists (vertices numbered $0 \dots n - 1$) or a `defaultdict(list)` (arbitrary hashable labels):

```python
from collections import defaultdict


def build_graph(n: int, edges: list[list[int]], directed: bool = False) -> list[list[int]]:
    graph: list[list[int]] = [[] for _ in range(n)]
    for u, v in edges:
        graph[u].append(v)
        if not directed:
            graph[v].append(u)
    return graph


def build_weighted(edges: list[tuple[str, str, int]]) -> dict[str, list[tuple[str, int]]]:
    graph: dict[str, list[tuple[str, int]]] = defaultdict(list)
    for u, v, w in edges:
        graph[u].append((v, w))
    return graph
```

A **grid** is an implicit graph: each cell is a vertex, and its neighbors are computed from coordinates, never stored.

```python
DIRECTIONS = [(0, 1), (1, 0), (0, -1), (-1, 0)]


def grid_neighbors(r: int, c: int, rows: int, cols: int):
    for dr, dc in DIRECTIONS:
        nr, nc = r + dr, c + dc
        if 0 <= nr < rows and 0 <= nc < cols:
            yield nr, nc
```

## Traversal: The Master Algorithm

Visiting every vertex and edge systematically is the foundation of nearly every graph algorithm. The key idea is to **mark** vertices so that we never get lost going around in circles. Each vertex passes through three states:

1. **Undiscovered** — not yet seen.
2. **Discovered** — seen, but its edges haven't all been explored.
3. **Processed** — all its edges have been explored.

Keep the discovered-but-unprocessed vertices in a container. Repeatedly take a vertex out, and for each edge leading to an undiscovered vertex, mark that vertex discovered and add it to the container.

Why does this visit everything reachable? Suppose some reachable vertex $u$ is never visited. Then some neighbor $v$ of $u$ on the path from the start *was* visited — but when $v$ was processed, it would have discovered $u$. Contradiction.

**Every traversal takes $O(V + E)$ time**: each vertex enters the container once, and each edge is examined once from each endpoint. That's optimal — you can't even *read* the graph faster. Anything you can do with one or two traversals is linear time.

The remarkable thing is that **the order of exploration is decided entirely by the container**:

- A **queue** (FIFO) explores the oldest discoveries first. Exploration radiates outward in rings from the start: **breadth-first search**.
- A **stack** (LIFO) explores the newest discoveries first. Exploration plunges down a path and backs up only when stuck: **depth-first search**.

For some problems the choice doesn't matter (reachability, counting components). For others it's everything: BFS finds shortest paths; DFS reveals cycles and dependency order.

## Breadth-First Search

```python
from collections import deque


def bfs(graph: list[list[int]], start: int) -> tuple[list[int], list[int]]:
    """Return (dist, parent): hop distance from start and the BFS tree (-1 = none)."""
    n = len(graph)
    dist = [-1] * n
    parent = [-1] * n
    dist[start] = 0
    queue = deque([start])
    while queue:
        u = queue.popleft()
        for v in graph[u]:
            if dist[v] == -1:              # undiscovered
                dist[v] = dist[u] + 1
                parent[v] = u
                queue.append(v)
    return dist, parent


def reconstruct_path(parent: list[int], target: int) -> list[int]:
    path = []
    while target != -1:
        path.append(target)
        target = parent[target]
    return path[::-1]
```

!!! warning "Mark when you *enqueue*, not when you dequeue"
    Marking a vertex as seen only when it's popped lets the same vertex be enqueued many times — once from each neighbor that discovers it before it's processed. On dense graphs and grids, this can blow up both time and memory.

### Shortest paths in unweighted graphs

BFS discovers vertices in order of increasing distance: all vertices at distance 1, then all at distance 2, and so on. So the first time a vertex is discovered, it's by a **shortest path**, and the parent pointers form a shortest-path tree rooted at the start. Two caveats: the tree gives shortest paths *from the start vertex only*, and only when **all edges have equal weight**.

**Shortest Path in Binary Matrix** (LC 1091) is BFS on an 8-connected grid; **Minimum Knight Moves** (LC 1197) is BFS on the implicit graph of knight moves.

### Multi-source BFS

To compute each vertex's distance to the **nearest** of several sources, put all the sources in the queue at distance 0 and run a single BFS. It's as if a super-source were connected to all of them with zero-length edges. **Rotting Oranges** (LC 994), **Walls and Gates** (LC 286), and **01 Matrix** (LC 542) all work this way.

```python
def oranges_rotting(grid: list[list[int]]) -> int:
    rows, cols = len(grid), len(grid[0])
    queue = deque((r, c) for r in range(rows) for c in range(cols) if grid[r][c] == 2)
    fresh = sum(row.count(1) for row in grid)
    minutes = 0
    while queue and fresh:
        minutes += 1
        for _ in range(len(queue)):                  # one ring = one minute
            r, c = queue.popleft()
            for nr, nc in grid_neighbors(r, c, rows, cols):
                if grid[nr][nc] == 1:
                    grid[nr][nc] = 2
                    fresh -= 1
                    queue.append((nr, nc))
    return -1 if fresh else minutes
```

### Two-coloring: is the graph bipartite? (LC 785)

A graph is **bipartite** if its vertices can be colored with two colors so that every edge joins different colors. Color the start vertex arbitrarily; every neighbor is then forced to take the other color, and so on outward. BFS propagates the forced colors; if some edge ever joins two vertices of the same color, no two-coloring exists. (Equivalently: a graph is bipartite iff it has no odd-length cycle.)

```python
def is_bipartite(graph: list[list[int]]) -> bool:
    color = [-1] * len(graph)
    for start in range(len(graph)):              # the graph may be disconnected
        if color[start] != -1:
            continue
        color[start] = 0
        queue = deque([start])
        while queue:
            u = queue.popleft()
            for v in graph[u]:
                if color[v] == -1:
                    color[v] = 1 - color[u]
                    queue.append(v)
                elif color[v] == color[u]:
                    return False
    return True
```

### Implicit graphs: searching a state space

Many puzzles are shortest-path problems on a graph that's never written down. The vertices are **states**, the edges are **moves**, and BFS generates neighbors on the fly.

**Open the Lock** (LC 752): a state is a 4-digit combination; each move turns one wheel up or down, giving 8 neighbors. The whole graph has $10^4$ vertices — small enough for BFS, though no one would build it explicitly.

```python
def open_lock(deadends: list[str], target: str) -> int:
    dead = set(deadends)
    if "0000" in dead:
        return -1
    seen = {"0000"}
    queue = deque([("0000", 0)])
    while queue:
        state, moves = queue.popleft()
        if state == target:
            return moves
        for i in range(4):
            d = int(state[i])
            for step in (1, -1):
                nxt = state[:i] + str((d + step) % 10) + state[i + 1:]
                if nxt not in seen and nxt not in dead:
                    seen.add(nxt)
                    queue.append((nxt, moves + 1))
    return -1
```

**Word Ladder** (LC 127) is the same idea with words as states and single-letter changes as moves. When the state space is large, **bidirectional BFS** — searching from both ends and stopping when the frontiers meet — explores roughly $2 b^{d/2}$ states instead of $b^d$.

## Depth-First Search

DFS is BFS with a stack instead of a queue — and since recursion *is* a stack, DFS has a beautifully short recursive form:

```python
def dfs_order(graph: list[list[int]], start: int) -> list[int]:
    visited: set[int] = set()
    order: list[int] = []

    def dfs(u: int) -> None:
        visited.add(u)
        order.append(u)                  # "process vertex early": pre-order
        for v in graph[u]:
            if v not in visited:
                dfs(v)
        # "process vertex late" would go here: post-order

    dfs(start)
    return order
```

DFS is essentially the same procedure as **backtracking** (see [Backtracking](13_backtracking.md)): advance whenever possible, back up only when every option is exhausted.

!!! warning "Recursion depth"
    Recursive DFS on a long path of $10^5$ vertices exceeds Python's recursion limit. For large graphs, either use an explicit stack or `sys.setrecursionlimit` (and be aware that very deep recursion can still crash the interpreter).

### Why DFS is special: entry/exit times and edge classes

Give DFS a clock that ticks each time a vertex is entered or exited. If $x$ is an ancestor of $y$ in the DFS tree, then $x$ is entered before $y$ and exited after $y$ — the intervals $[\text{entry}, \text{exit}]$ nest like parentheses.

More importantly, DFS sorts the edges of an **undirected** graph into just two classes:

- **Tree edges**, which discover new vertices.
- **Back edges**, which lead to an **ancestor** in the DFS tree.

There are no "cross edges" between unrelated branches. Why? If $u$ has an edge to $v$ and $v$ is still undiscovered when $u$ is explored, DFS will discover $v$ *from* $u$ — making it a tree edge. By the time DFS leaves $u$, everything reachable from $u$ has been explored.

!!! tip "Take-Home Lesson"
    DFS organizes vertices by entry and exit times, and edges into tree and back edges. That organization — not the traversal itself — is where DFS gets its power: cycle detection, topological sorting, articulation points, and strongly connected components all come from it.

### Connected components and flood fill

Starting a traversal from each still-unvisited vertex partitions the graph into its **connected components**. A surprising number of problems reduce to counting or labeling components. **Number of Islands** (LC 200) is exactly this on a grid:

```python
def num_islands(grid: list[list[str]]) -> int:
    rows, cols = len(grid), len(grid[0])

    def sink(r: int, c: int) -> None:
        stack = [(r, c)]                        # iterative: islands can be large
        grid[r][c] = "0"
        while stack:
            r, c = stack.pop()
            for nr, nc in grid_neighbors(r, c, rows, cols):
                if grid[nr][nc] == "1":
                    grid[nr][nc] = "0"          # mark on discovery
                    stack.append((nr, nc))

    islands = 0
    for r in range(rows):
        for c in range(cols):
            if grid[r][c] == "1":
                islands += 1
                sink(r, c)
    return islands
```

**Reverse the question.** In **Surrounded Regions** (LC 130), rather than asking "is this region surrounded?", flood-fill from every border `O` and mark what's reachable; everything unmarked is surrounded. In **Pacific Atlantic Water Flow** (LC 417), rather than simulating water flowing downhill from every cell, flow *uphill* from each ocean's border and intersect the two reachable sets. Starting from the targets is often dramatically simpler than starting from every source.

### Cycle detection

**Undirected graphs:** a cycle exists iff DFS finds a back edge — an edge to an already-visited vertex *other than the parent* (the edge we came in on is not a cycle).

**Directed graphs:** a cycle exists iff DFS finds an edge to a vertex that is **discovered but not yet processed** — an ancestor still on the recursion stack. An edge to a fully processed vertex is harmless (a forward or cross edge). Three colors track this:

```python
WHITE, GRAY, BLACK = 0, 1, 2       # undiscovered, on the stack, processed


def has_cycle_directed(graph: list[list[int]]) -> bool:
    color = [WHITE] * len(graph)

    def dfs(u: int) -> bool:
        color[u] = GRAY
        for v in graph[u]:
            if color[v] == GRAY:                 # back edge to an ancestor
                return True
            if color[v] == WHITE and dfs(v):
                return True
        color[u] = BLACK
        return False

    return any(color[u] == WHITE and dfs(u) for u in range(len(graph)))
```

Using just a `visited` set for directed graphs is a classic bug: in the graph $a \to b$, $a \to c$, $c \to b$, reaching $b$ a second time is not a cycle.

## Topological Sorting

A **topological order** of a directed graph lists its vertices so that every edge points **forward**, from earlier to later. If edges mean "must happen before," a topological order is a valid schedule. It exists **iff the graph is a DAG**: a cycle would require going forward forever and still returning to the start.

Topological sorting is the most important operation on DAGs, because it lets you process each vertex after everything that points to it. Shortest paths, longest paths, and counting paths in a DAG all become a single left-to-right pass in topological order — even with negative weights.

### Via DFS: reverse post-order

List the vertices in the order DFS *finishes* them, then reverse. Why is that a topological order? Consider any edge $(x, y)$ at the moment DFS explores it from $x$:

- If $y$ is undiscovered, DFS finishes $y$ before returning to finish $x$. ✓
- If $y$ is already finished, it finished before $x$ will. ✓
- If $y$ is discovered but unfinished, it's an ancestor on the stack — a back edge, which means a cycle, which is impossible in a DAG.

In every legal case, $y$ finishes before $x$, so after reversing, $x$ comes before $y$.

### Via in-degrees: Kahn's algorithm

A vertex with no incoming edges can safely go first. Remove it, which may free up others, and repeat. If vertices remain but none has in-degree zero, they contain a cycle.

```python
def topological_sort(n: int, edges: list[list[int]]) -> list[int] | None:
    """Kahn's algorithm. edges[i] = [u, v] means u must come before v."""
    graph: list[list[int]] = [[] for _ in range(n)]
    indegree = [0] * n
    for u, v in edges:
        graph[u].append(v)
        indegree[v] += 1
    queue = deque(u for u in range(n) if indegree[u] == 0)
    order = []
    while queue:
        u = queue.popleft()
        order.append(u)
        for v in graph[u]:
            indegree[v] -= 1
            if indegree[v] == 0:
                queue.append(v)
    return order if len(order) == n else None      # None: there's a cycle
```

**Course Schedule** (LC 207) asks whether the order exists; **Course Schedule II** (LC 210) asks for it. Kahn's algorithm also answers "what's the minimum number of semesters?" (process the queue level by level, as in BFS) and "is the order unique?" (the queue never holds more than one vertex).

??? question "Stop and Think: Ordering the fragments"
    **Problem:** A DNA sequencing experiment produces fragments. For some pairs you know that fragment $a$ must lie to the left of fragment $b$. Find a left-to-right ordering consistent with all the constraints.

    **Solution:** Make each fragment a vertex, and add a directed edge $a \to b$ for each "left of" constraint. A consistent ordering is exactly a topological sort of this graph; if the graph has a cycle, the constraints are contradictory. **Alien Dictionary** (LC 269) is the same problem: compare adjacent words to extract "letter $x$ comes before letter $y$" edges, then topologically sort the letters.

### Strongly connected components

A directed graph is **strongly connected** if every vertex can reach every other. Its **strongly connected components** (SCCs) are the maximal strongly connected pieces, and contracting each SCC to a single vertex always leaves a DAG. **Kosaraju's algorithm** finds them with two DFS passes: record finish order on $G$, then DFS the **reversed** graph in decreasing finish order — each search tree is one SCC.

```python
def strongly_connected_components(graph: list[list[int]]) -> list[list[int]]:
    n = len(graph)
    finished: list[int] = []
    seen = [False] * n

    for s in range(n):                               # pass 1: finish order on G
        if seen[s]:
            continue
        seen[s] = True
        stack = [(s, iter(graph[s]))]
        while stack:
            u, it = stack[-1]
            v = next(it, None)
            if v is None:
                stack.pop()
                finished.append(u)
            elif not seen[v]:
                seen[v] = True
                stack.append((v, iter(graph[v])))

    reverse: list[list[int]] = [[] for _ in range(n)]
    for u in range(n):
        for v in graph[u]:
            reverse[v].append(u)

    comp = [-1] * n
    components = []
    for s in reversed(finished):                     # pass 2: DFS on reversed G
        if comp[s] != -1:
            continue
        comp[s] = len(components)
        members, stack = [], [s]
        while stack:
            u = stack.pop()
            members.append(u)
            for v in reverse[u]:
                if comp[v] == -1:
                    comp[v] = comp[s]
                    stack.append(v)
        components.append(members)
    return components
```

(The first pass uses an explicit stack of iterators to get correct finish times without recursion.)

### Weak points: bridges and articulation vertices

An **articulation vertex** is one whose removal disconnects the graph; a **bridge** is such an edge. They are single points of failure in a network (LC 1192, Critical Connections). DFS finds all of them in one pass using a single extra number per vertex: $\text{low}(u)$, the earliest entry time reachable from $u$'s subtree using **at most one back edge**. A tree edge $(u, v)$ is a bridge iff $\text{low}(v) > \text{entry}(u)$ — nothing below $v$ can climb back above it.

```python
def critical_connections(n: int, connections: list[list[int]]) -> list[list[int]]:
    graph = build_graph(n, connections)
    entry = [-1] * n
    low = [0] * n
    bridges = []
    timer = 0

    def dfs(u: int, parent: int) -> None:
        nonlocal timer
        entry[u] = low[u] = timer
        timer += 1
        for v in graph[u]:
            if v == parent:
                continue
            if entry[v] == -1:                       # tree edge
                dfs(v, u)
                low[u] = min(low[u], low[v])
                if low[v] > entry[u]:
                    bridges.append([u, v])
            else:                                    # back edge
                low[u] = min(low[u], entry[v])

    for s in range(n):
        if entry[s] == -1:
            dfs(s, -1)
    return bridges
```

## Minimum Spanning Trees

A **spanning tree** of a connected graph is a subset of $V - 1$ edges connecting all the vertices without a cycle. The **minimum spanning tree** (MST) is the one of least total weight: the cheapest way to connect everything — cities with roads, houses with cable, points with wire.

Two greedy algorithms find it. Greedy algorithms are usually suspect (see [Intervals](08_intervals.md#three-plausible-ideas-three-failures)), so both come with a proof. The key fact behind both:

> **Cut property.** Split the vertices into two groups. The lightest edge crossing between them belongs to some MST.

*Proof by exchange:* take an MST that doesn't contain the lightest crossing edge $e$. Adding $e$ creates a cycle, and that cycle must cross the split a second time through some edge $f$. Since $e$ is the lightest crossing edge, $w(e) \le w(f)$. Swapping $f$ for $e$ gives a spanning tree no heavier than before — so an MST containing $e$ exists.

### Prim's algorithm

Grow a single tree from any start vertex. Repeatedly add the **cheapest edge leaving the tree** — the lightest edge across the cut (tree, everything else). A heap holds the candidate edges; stale entries for vertices already in the tree are skipped.

```python
import heapq


def prim_mst_weight(n: int, graph: list[list[tuple[int, int]]]) -> int:
    """graph[u] = [(v, w), ...] for an undirected connected graph."""
    in_tree = [False] * n
    heap = [(0, 0)]                                  # (edge weight, vertex)
    total = 0
    while heap:
        w, u = heapq.heappop(heap)
        if in_tree[u]:
            continue                                 # stale entry
        in_tree[u] = True
        total += w
        for v, wv in graph[u]:
            if not in_tree[v]:
                heapq.heappush(heap, (wv, v))
    return total
```

$O(E \log V)$ with a heap. For dense graphs — such as **Min Cost to Connect All Points** (LC 1584), where every pair of points is an edge — a simple $O(V^2)$ array-based Prim is faster, since it never materializes the $V^2$ edges.

### Kruskal's algorithm

Sort all edges by weight. Take each edge in order, **unless it would close a cycle**. Each accepted edge is the lightest crossing the cut between its endpoint's components. To check "would this close a cycle?" — are the endpoints already in the same component? — use a **union-find** structure (see [Trie & Union Find](12_trie_union_find.md)), which answers it in nearly constant time.

```python
def kruskal_mst_weight(n: int, edges: list[tuple[int, int, int]]) -> int:
    parent = list(range(n))

    def find(x: int) -> int:
        while parent[x] != x:
            parent[x] = parent[parent[x]]            # path halving
            x = parent[x]
        return x

    total = used = 0
    for w, u, v in sorted(edges):                    # edges as (weight, u, v)
        ru, rv = find(u), find(v)
        if ru != rv:
            parent[ru] = rv
            total += w
            used += 1
            if used == n - 1:
                break
    return total
```

$O(E \log E)$, dominated by the sort. Kruskal is usually the simpler choice for sparse graphs given as an edge list.

Variations fall out of the same algorithms: a **maximum** spanning tree is an MST on negated weights; the **minimax path** (minimize the heaviest edge on a path) follows the MST; and stopping Kruskal early at $k$ components gives **single-linkage clustering**.

## Shortest Paths

BFS finds shortest paths only when every edge costs the same. With weights, the shortest path might use many cheap edges rather than a few expensive ones.

### Dijkstra's algorithm

Dijkstra's algorithm is Prim's algorithm with a different notion of "cheapest." Prim adds the vertex attached by the **lightest edge**; Dijkstra adds the vertex with the smallest **total distance from the source**. It maintains tentative distances and repeatedly finalizes the closest unfinalized vertex, relaxing its outgoing edges.

```python
def dijkstra(graph: list[list[tuple[int, int]]], source: int) -> list[float]:
    dist = [float("inf")] * len(graph)
    dist[source] = 0
    heap = [(0, source)]
    while heap:
        d, u = heapq.heappop(heap)
        if d > dist[u]:
            continue                        # stale entry: u already finalized with a shorter d
        for v, w in graph[u]:
            if d + w < dist[v]:             # relax edge (u, v)
                dist[v] = d + w
                heapq.heappush(heap, (dist[v], v))
    return dist
```

**Time:** $O((V + E) \log V)$. Python's `heapq` can't decrease a key, so this uses **lazy deletion**: push a new entry on every improvement and skip entries that are out of date when popped.

**Why it's correct:** when $u$ is popped with distance $d$, every other path to $u$ must leave the set of finalized vertices through some vertex whose tentative distance is already $\ge d$ (otherwise *it* would have been popped first), and continuing from there can only add more. That argument needs one assumption: **no negative edges**. A negative edge could make a longer-looking detour cheaper after $u$ was already finalized. (If the bank paid you to walk through its lobby, the shortest way to your neighbor's house might involve walking through it forever.)

Dijkstra adapts to many "shortest" notions, as long as extending a path never makes it better:

- **Path With Minimum Effort** (LC 1631): the cost of a path is its *maximum* step, so relax with `max(d, w)` instead of `d + w`.
- **Path with Maximum Probability** (LC 1514): maximize a product of probabilities — use a max-heap, or Dijkstra on $-\log p$.
- **Swim in Rising Water** (LC 778): minimize the maximum elevation along a path.

??? question "Stop and Think: Costs on vertices instead of edges"
    **Problem:** In a directed graph, each **vertex** has a cost, and a path's cost is the sum of the costs of the vertices on it. Find the cheapest path from $s$ to $t$.

    **Solution:** You could modify Dijkstra's code to add vertex costs. But it's cleaner to leave the algorithm alone and **change the graph**: give each directed edge $(u, v)$ the weight $\text{cost}(v)$. Every path's edge weight now equals the sum of its vertex costs (plus $\text{cost}(s)$, a constant). Plain Dijkstra does the job. This is "design graphs, not algorithms" in miniature.

### Negative edges and limited hops: Bellman–Ford

**Bellman–Ford** relaxes *every* edge, $V - 1$ times. After round $k$, every shortest path using at most $k$ edges has been found; since shortest paths (without negative cycles) use at most $V - 1$ edges, that's enough. If a $V$-th round still improves something, there's a **negative cycle**. $O(VE)$.

The round structure is useful in its own right. **Cheapest Flights Within K Stops** (LC 787) wants the cheapest path with at most $k + 1$ edges — exactly $k + 1$ rounds of Bellman–Ford, relaxing from a snapshot of the previous round so that each round extends paths by only one edge:

```python
def find_cheapest_price(n: int, flights: list[list[int]], src: int, dst: int, k: int) -> int:
    dist = [float("inf")] * n
    dist[src] = 0
    for _ in range(k + 1):
        prev = dist[:]                       # distances using one fewer edge
        for u, v, w in flights:
            if prev[u] + w < dist[v]:
                dist[v] = prev[u] + w
    return -1 if dist[dst] == float("inf") else int(dist[dst])
```

### All pairs: Floyd–Warshall

To get the distance between **every** pair of vertices, number the vertices and let $D_k[i][j]$ be the shortest path from $i$ to $j$ whose intermediate vertices all come from $\{0, \dots, k\}$. Allowing vertex $k$ as a new intermediate either helps or it doesn't:

$$D_k[i][j] = \min\big(D_{k-1}[i][j],\ D_{k-1}[i][k] + D_{k-1}[k][j]\big)$$

This is dynamic programming (see [Dynamic Programming](15_dynamic_programming.md)), and the code is three nested loops:

```python
def floyd_warshall(n: int, edges: list[tuple[int, int, int]]) -> list[list[float]]:
    INF = float("inf")
    dist = [[0 if i == j else INF for j in range(n)] for i in range(n)]
    for u, v, w in edges:
        dist[u][v] = min(dist[u][v], w)
    for k in range(n):                       # k MUST be the outermost loop
        for i in range(n):
            for j in range(n):
                if dist[i][k] + dist[k][j] < dist[i][j]:
                    dist[i][j] = dist[i][k] + dist[k][j]
    return dist
```

$O(V^3)$ — no better asymptotically than running Dijkstra from every vertex, but the loops are so tight that it's often faster for $V$ up to a few hundred. It handles negative edges (not negative cycles), and it computes **transitive closure** — which vertices can reach which — as a byproduct: $i$ reaches $j$ iff $D[i][j] < \infty$.

### Which shortest-path algorithm?

| Situation | Algorithm | Time |
|---|---|---|
| Unweighted (or all weights equal) | BFS | $O(V + E)$ |
| Weights 0 or 1 | 0-1 BFS (deque: push 0-edges front, 1-edges back) | $O(V + E)$ |
| DAG, any weights | Relax edges in topological order | $O(V + E)$ |
| Non-negative weights | Dijkstra | $O(E \log V)$ |
| Negative edges, or at most $k$ edges | Bellman–Ford | $O(VE)$ or $O(kE)$ |
| All pairs, $V \lesssim 400$ | Floyd–Warshall | $O(V^3)$ |

## Network Flow and Matching (Briefly)

Think of each edge as a pipe with a **capacity**. The **maximum flow** from $s$ to $t$ is the most material that can be pushed through the network at once, and the **max-flow min-cut theorem** says it equals the total capacity of the cheapest set of edges whose removal separates $s$ from $t$. Flow algorithms (Ford–Fulkerson with BFS augmenting paths, Edmonds–Karp) solve connectivity problems and, crucially, **bipartite matching**: add a source connected to one side and a sink connected to the other, all capacities 1, and the maximum flow is the largest matching. Flow problems are uncommon in interviews but worth recognizing — "assign workers to jobs," "how many edges must be cut" — because the reduction is often the whole solution.

## Design Graphs, Not Algorithms

The hardest part of most graph problems is noticing that they are graph problems, and choosing the vertices and edges so that a standard algorithm answers the question. Some examples:

| Problem | Vertices | Edges | Algorithm |
|---|---|---|---|
| Word Ladder (LC 127) | Words | Differ by one letter | BFS |
| Open the Lock (LC 752) | 4-digit combinations | One wheel turn | BFS |
| Bus Routes (LC 815) | **Routes** (not stops!) | Routes sharing a stop | BFS from routes containing the source |
| Evaluate Division (LC 399) | Variables | $a \xrightarrow{a/b} b$, $b \xrightarrow{b/a} a$ | DFS multiplying weights |
| Cheapest Flights Within K Stops (LC 787) | (city, stops used) | Flights | Dijkstra / Bellman–Ford |
| Shortest Path to Get All Keys (LC 864) | (cell, keys held as a bitmask) | Grid moves | BFS |
| Reconstruct Itinerary (LC 332) | Airports | Tickets | Eulerian path (Hierholzer) |
| Minimum rooms / buckets for overlapping items | Items | Overlaps | Graph coloring |

Two recurring tricks stand out. First, **the obvious vertices are not always the right ones**: in Bus Routes, making each route a vertex turns "fewest buses" into plain BFS. Second, **when a constraint depends on history, put the history into the state**: "at most $k$ stops" or "holding these keys" become part of the vertex, and the enlarged graph is searched with the ordinary algorithm.

## Common Mistakes

1. **Marking visited on dequeue in BFS.** Vertices get enqueued repeatedly; mark them when first discovered.

2. **Using a plain visited set for directed cycle detection.** An edge to a finished vertex is not a cycle. Track "on the current DFS path" separately (gray vs. black).

3. **Using BFS on weighted graphs.** BFS minimizes the number of edges, not their total weight.

4. **Dijkstra with negative edges.** It silently returns wrong answers. Use Bellman–Ford, or topological order if the graph is a DAG.

5. **Forgetting disconnected graphs.** A single traversal only covers one component. Loop over all vertices when you need the whole graph (components, bipartiteness, cycle detection, topological sort).

6. **Building huge implicit graphs explicitly.** Generate neighbors on demand. For grids, check bounds instead of storing edges.

7. **Deep recursion.** Recursive DFS on large graphs hits Python's recursion limit. Use an explicit stack when depth can reach the thousands.

8. **Wrong loop order in Floyd–Warshall.** The intermediate vertex $k$ must be the **outer** loop.
